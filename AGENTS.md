# Agent Guide — platform-external-capi

This file governs a **planning and multi-repo working area** for adding Cluster API (CAPI)
infrastructure provisioning to OpenShift's `platform: external`.

**This file is checked in to `installer-labs`, but it describes the directory *above* it.**
That parent — the workspace root — is not itself a git repository; every entry in the table
below, including `installer-labs` itself, is an independent clone or an untracked working
directory sitting side by side in it. Paths in this document are written relative to this
file, so the workspace root is `../`.

Read this file before working here. Per-repo guidance still applies inside each clone
(for example [../installer/AGENTS.md](../installer/AGENTS.md)).

## Rules

### Never read secret material — not even once

**This rule is absolute and comes before task completion.** Anything an agent reads enters
a conversation transcript and may be cached by a model provider. A secret read once is
compromised regardless of what happens afterwards, and it cannot be unread. If following
this rule blocks a task, **the task stops and the human is asked** — it is never traded
away for progress.

Never read, print, echo, decode or otherwise cause the *contents* of these to appear in
any output:

| Never read the contents of | Where it shows up here |
| --- | --- |
| AWS credentials, **especially `$AWS_SHARED_CREDENTIALS_FILE`** | `install-dirs/run-create-command.sh` points it at a file under `~/.aws/` |
| `pullSecret` in any install-config | `install-dirs/install-config.yaml` and every copy under `install-dir-*/` |
| `sshKey`, and any private key | same files |
| `.kubeconfig`, `auth/` directories, any `*.pem`, `*.key` | produced by installs under `install-dir-*/` |
| Anything in a local CAPI control plane's Secrets | envtest state during a run |
| **Any manifest tree generated by `create manifests`** | `install-dirs/sample-aws-manifests/` and `install-dir-*/manifests/`, `install-dir-*/openshift/` |

**Paths and variable names are not secrets; values are.** Using
`AWS_SHARED_CREDENTIALS_FILE` is expected and encouraged — export it, pass it to a
command, let the installer read it. The prohibition is on the agent looking inside.
`echo $AWS_SHARED_CREDENTIALS_FILE` is fine. `cat $AWS_SHARED_CREDENTIALS_FILE` is not.

#### What this rules out in practice

- **Do not use `Read` or `Edit` on a file containing a secret.** `Edit` requires a prior
  `Read` of the whole file, so it is prohibited on `install-config.yaml` for as long as
  that file carries a `pullSecret`. Use targeted shell edits (`sed -i`, `yq -i`) instead —
  they modify in place without emitting content.
- **Do not `cat`, `head`, `tail`, `less` or `grep` without restricting the output.**
  `grep -c`, `grep -o` on a non-secret pattern, and `grep -n | cut -d: -f1` are safe
  because they cannot emit a value. Plain `grep pullSecret` is not.
- **Do not paste installer debug output containing an install-config dump.** Redact at the
  point of capture, not afterwards.
- **Do not add `set -x` to a script that interpolates a secret**, and do not remove it from
  one that only handles paths — the existing `set -eux` in
  [install-dirs/run-create-command.sh](../install-dirs/run-create-command.sh) traces paths
  only, which is fine.

#### How to inspect a file that holds a secret

Ask only the question you need, in a form whose answer cannot be the secret:

```sh
grep -c '^pullSecret:' install-config.yaml           # is it present?
grep -oE '^[a-zA-Z]+:' install-config.yaml | sort -u # what keys exist?
grep -nE '^(pullSecret|sshKey):' install-config.yaml | cut -d: -f1   # which lines?
```

**A range `sed` is not one of these forms, and an earlier version of this file wrongly
listed one as safe.** `sed -n '/^compute:/,/^networking:/p' install-config.yaml`, run to
print the compute stanza, printed the `pullSecret` and the `sshKey` — because in that file
both sit between those two keys. The range's endpoints say nothing about what lies between
them, so the output is bounded by the file's key order, which the agent did not check and
cannot rely on. A `/^platform:/,/^[a-zA-Z]/` range is the same construct and fails the same
way the moment a key moves. Use a form whose output is bounded by the *pattern*, not by the
document: `grep -c`, `grep -o` on a non-secret pattern, `grep -n | cut -d: -f1`. If a whole
subtree is genuinely needed, it is a sign the secret does not belong in that file — apply
the structural fix below instead.

`yq` is **not installed** in this workspace; do not write instructions that assume it.

#### A generated manifest tree is a secret-bearing artifact, and it looks like a sample

**The output of `create manifests` is a credential store.** `install-dirs/sample-aws-manifests/`
holds, unredacted: the machine-config-server **TLS private key**, a **CA private key**, the
**pull secret**, **cloud credentials** and the **kubeadmin password hash**. Nothing about its
appearance warns you — it is a directory of plausibly-named YAML, indistinguishable at a
glance from a hand-authored sample.

On this platform the temptation is sharper than elsewhere, because the central partner-facing
question is *"what should my manifests look like?"* and the cheapest honest-seeming answer is
to show a real set. **Never publish a captured tree. A sample is hand-written with
placeholders.** Inspect a generated tree by filename and size only.

#### Verify a redaction by the secret's shape, never by the placeholder's presence

`sshKey` in the install-config template was a **block scalar**. A line-oriented
`sed -i 's|^sshKey: .*|sshKey: ""|'` replaced the `sshKey: |` line and left the key material
on a dangling continuation line — producing a file that **still contained the key** *and* was
now invalid YAML. A check for `sshKey: ""` returned a clean `1` and would have passed.

**An edit that lands fully and an edit that lands halfway are indistinguishable from the
placeholder's side.** So after any redaction, ask the opposite question:

```sh
grep -cE 'ssh-(rsa|ed25519|dss)' install-config.yaml      # must be 0
grep -cE 'BEGIN [A-Z ]*PRIVATE KEY' <file>                # must be 0
```

Both checks must run, and they must agree. If they disagree, the redaction failed.
And treat "someone said it was redacted" as a hypothesis, never as a result.

#### Preferred: keep the secret out of the file the agent works with

The structural fix, better than any discipline: the template carries a placeholder and
the real value is injected into the per-run copy by a command that never prints it.

```sh
# install-config.yaml (template, agent-editable, no secret in it)
pullSecret: ""
```

```sh
# injected into the copy; nothing is written to stdout, so nothing is ingested
python3 - "${INSTALL_DIR}/install-config.yaml" "${PULL_SECRET_FILE}" <<'PY'
import json, pathlib, sys
cfg, secret = pathlib.Path(sys.argv[1]), pathlib.Path(sys.argv[2])
# json.dumps emits a correctly escaped double-quoted scalar, which is valid YAML.
cfg.write_text(cfg.read_text().replace(
    'pullSecret: ""', 'pullSecret: ' + json.dumps(secret.read_text().strip()), 1))
PY
```

The template then becomes a normal file an agent can `Read` and `Edit` freely, and only
the generated per-run copy is off limits. `PULL_SECRET_FILE` lives outside this workspace,
alongside the AWS credentials file.

#### Never write a secret outward

No credential, pull secret, key or customer-specific value goes into a plan HTML, a
divergence record, a commit message, a PR description, a test fixture or an installer log
line. The existing logging rule — **artifact path, source and SHA-256 only, never file
contents** — is the same rule seen from the code's side.

### Plan files are append-only

**Never edit a published `vN` HTML in place. Always emit `vN+1`.** Every change to a plan
goes through a written change instruction in
[implementation-plans/](../implementation-plans/), then through the `plan-new-version` skill.
This is also encoded as Appendix A inside the plan documents themselves.

### Every code claim is cited and verified

Plan versions v3 and v4 were written without a local checkout and contain claims that do
not match the code. Any statement about installer behaviour must cite `file:line` and be
checked against the local clone at a recorded commit. Where something cannot be verified,
say so explicitly — do not delete it and do not restate it as fact.

### Keep the installer clone clean

This workspace's tooling lives here, at the workspace root — never inside
[installer/](../installer/). That clone is a fork intended for upstream pull requests and its
`git status` should stay clean of workspace scaffolding.

**The rule has a second direction, and it is the one that bites.** Material deliberately
copied *into* the clone — as `installer/upi/external/` was — must pass the clone's own gates,
which are not the gates it passed outside. Copying pilot YAML in introduced **15 `yamllint`
errors** into a repository that had zero, all of them `indent-sequences: false` violations
that are **semantically a no-op** and that four successful cluster installs never noticed.

Before anything new inside [installer/](../installer/) is called done, run the gates it now
belongs to:

```sh
cd installer && hack/yaml-lint.sh && hack/shellcheck.sh
```

`hack/shellcheck.sh` **already exits 1 on master** over a pre-existing `SC1117` in
`data/data/bootstrap/files/usr/local/bin/konnectivity-certs.sh`. Compare against that
baseline rather than against exit 0, and say which findings are yours.

When fixing a lint error in a file that is *also* a tested artifact, **prove the fix is
semantically inert** — parse before and after and require equal objects — rather than trusting
that the linter's complaint was cosmetic. And do not blanket-fix `SC2086`: some lines rely on
glob expansion, where quoting the whole word breaks working automation. Quote the variable,
not the word.

### Publishing is its own increment

A change that touches no installer logic and spends nothing can still carry credential and
gate failures, and those failures are not found by installing another cluster. When producing
anything partner-facing, treat it as an increment with its own test arms — see
`external-platform-installer-capi-enhancement-v14.html` §14 for the arms that were actually
run, and `installer/upi/external/examples/aws-capa/README.md` for the "before publication"
checklist pattern. Examples are named `examples/<cloud>-<capi-provider-short-name>/`:
`aws-capa`, `oci-capoci`, `azure-capz`.

### Distinguish local from target

The installer's CAPI control plane (envtest etcd + kube-apiserver) is **temporary and
local**. Resources in it, especially Secrets, do not reach the cluster being installed.
Never describe local CAPI state as if it were delivered to the target cluster.
